# Data Model and Intended Schema

## Read this first

A deployed SQLite WAL schema **v1** is shipped (`src/infrastructure/sqlite.rs`
`SCHEMA_V1`, `PRAGMA user_version = 1`, `journal_mode=WAL`,
`synchronous=NORMAL`, `busy_timeout 5s`). Default `sqlite` persistence stores
all entities durably; `InMemoryRepositories` remains available via
`APP_PERSISTENCE=memory` for tests. The NenDB material below defines the
logical behavior a future adapter would need after NenDB itself and its
integration path are verified. Collection names, index syntax, transaction APIs,
and data types are not claims about NenDB capabilities.

See the [logical ER diagram](diagrams/data-model-er.md).

## Current domain model

All IDs are UUID v7 values generated by the application. Timestamps are UTC.

### User

| Field | Rust type | Current behavior |
| --- | --- | --- |
| `id` | `Uuid` | Primary logical identity. |
| `email` | `String` | Trimmed and ASCII-lowercased before lookup/create. The in-memory adapter rejects duplicates while holding its write lock. |
| `password_hash` | `String` | Argon2 PHC string; excluded from serialization. |
| `created_at` | `DateTime<Utc>` | Set by the application at registration. |

### Resume

| Field | Rust type | Current behavior |
| --- | --- | --- |
| `id` | `Uuid` | Primary logical identity. |
| `user_id` | `Uuid` | Owner identity derived from the authenticated token. |
| `title` | `Option<String>` | Caller title after trimming, or the parser's first non-empty line. |
| `raw_text` | `String` | Sensitive source text; excluded from API serialization. |
| `skills` | `Vec<String>` | Deterministically extracted, sorted known skills. |
| `embedding` | `Vec<f32>` | Local 64-dimensional or externally supplied vector; excluded from API serialization. |
| `created_at` | `DateTime<Utc>` | Set by the application at ingestion. |

### Job

| Field | Rust type | Current behavior |
| --- | --- | --- |
| `id` | `Uuid` | Primary logical identity. |
| `owner_id` | `Uuid` | Creator identity derived from the authenticated token. |
| `title` | `String` | Trimmed after validation. |
| `description` | `String` | Sensitive source text; excluded from API serialization. |
| `skills` | `Vec<String>` | Deterministically extracted, sorted known skills. |
| `embedding` | `Vec<f32>` | Local or externally supplied vector; excluded from API serialization. |
| `created_at` | `DateTime<Utc>` | Set by the application at ingestion. |

### Recommendation

`Recommendation` is derived at request time from one job and one resume. It
contains `job_id`, `resume_id`, cosine `score`, `matched_skills`, and
`missing_skills`. It is not persisted and should not have a collection in the
first durable adapter. A cache would need explicit model/version, invalidation,
and authorization semantics before it could become authoritative.

## Current constraints and limits

- Registration email must validate as an email address. Password length is 12 to
  128. Login accepts password length 1 to 128.
- Resume title length is at most 200. Raw text length is 20 to 100,000.
- Job title length is 2 to 200. Description length is 20 to 100,000.
- The HTTP body limit is 512 KiB, independently of field validation.
- Recommendation `limit` defaults to 10 and must be between 1 and 100.
- The current repository model has no update, delete, pagination, optimistic
  concurrency, schema version, or idempotency-key operations.

The in-memory maps do not enforce foreign keys. Ownership is established by the
application because authenticated user IDs are supplied when resumes and jobs are
created. A durable adapter still needs a policy for orphan prevention and deletion.

## Intended logical collections

These are minimum logical records, not executable NenDB DDL.

### `users`

| Logical field | Requirement |
| --- | --- |
| `id` | UUID v7 encoded losslessly as a native UUID or canonical string; primary document key. |
| `email` | Normalized string; unique and case-sensitive after application normalization. |
| `password_hash` | Complete Argon2 PHC string; never indexed or logged. |
| `created_at` | UTC instant with enough precision for lossless application round trips. |

### `resumes`

| Logical field | Requirement |
| --- | --- |
| `id` | UUID v7 primary document key. |
| `user_id` | Owning user ID. |
| `title` | Nullable string. |
| `raw_text` | Sensitive text, up to the validated application limit. |
| `skills` | Ordered string array. Preserve order even though current parsing sorts it. |
| `embedding` | Ordered finite 32-bit float vector with exact dimension preservation. |
| `created_at` | UTC instant. |

### `jobs`

| Logical field | Requirement |
| --- | --- |
| `id` | UUID v7 primary document key. |
| `owner_id` | Owning user ID. |
| `title` | Non-null string. |
| `description` | Sensitive text, up to the validated application limit. |
| `skills` | Ordered string array. |
| `embedding` | Ordered finite 32-bit float vector with exact dimension preservation. |
| `created_at` | UTC instant. |

For durable model changes, add a schema version and embedding provenance such as
model identifier and vector dimensions. Those fields are not present in the
current Rust entities or repository signatures, so storing them reliably requires
an explicit domain/contract change rather than hidden adapter assumptions.

## Intended indexes

Index names below are descriptive placeholders. Exact NenDB syntax and support
must be confirmed before implementation.

| Collection | Logical index | Required behavior | Port supported |
| --- | --- | --- | --- |
| `users` | Primary `id` | Exact lookup by ID. | `find_by_id` |
| `users` | Unique `email` | Exact lookup and atomic duplicate rejection. | `find_by_email`, `create` |
| `resumes` | Primary `id` | Exact lookup by ID. | `find_by_id` |
| `resumes` | `user_id` plus stable tie-breaker `id` | Efficiently return all resumes for one user with deterministic paging available later. | `list_by_user` |
| `jobs` | Primary `id` | Exact lookup by ID. | `find_by_id` |
| `jobs` | `created_at` plus `id` | Stable full-list traversal if `list` remains part of the contract. | `list` |

The current ports return unbounded `Vec` values and do not expose cursors. Before
large datasets, evolve list methods to bounded pagination. An adapter must not hide
an unbounded full collection scan behind a method that appears inexpensive.

No vector index is required for current behavior because matching loads a user's
resumes and scores them in the Rust process. Introducing NenDB-native vector search
would change ranking, filtering, ownership, and likely the repository contract; it
requires a separate design and equivalence tests.

## Atomicity and transaction requirements

| Use case | Minimum intended guarantee |
| --- | --- |
| Register user | The unique email check and insert must be race-safe. Prefer one atomic conditional insert backed by the unique index. Map a uniqueness violation to `DomainError::Conflict`. The application's pre-read is not sufficient under concurrency. |
| Create resume | One all-or-nothing document create. Parsing and embedding happen before persistence and are not part of a database transaction. |
| Create job | One all-or-nothing document create. Parsing and embedding happen before persistence. |
| Authenticate | A consistent exact user read is sufficient. A missing user returns `Ok(None)` and becomes unauthorized at the application layer. |
| Recommend | Read job, authorize ownership, then read that owner's resumes. A snapshot is desirable if updates/deletes are later added, but the current port does not require or expose one. |

Do not assume NenDB supports multi-document transactions. Verify whether atomic
document creation and unique indexes provide the minimum guarantees. If they do
not, introduce an explicit gateway or revise the application contract rather than
emulating correctness with a process-local lock, which would fail across replicas.

Repository retries must be conservative. Reads may be retried for transient
failures when the protocol supports safe retries. A create may only be retried
with the same application-generated ID and a way to distinguish an existing
identical write from a conflicting record. An unknown write outcome must not be
blindly replayed as a new entity.

## Adapter contract

A future adapter implements the existing traits without exposing NenDB-specific
types. Required method semantics are:

| Method | Contract |
| --- | --- |
| `UserRepository::create` | Persist the complete user exactly once; return the stored value; return `Conflict` for duplicate ID or normalized email. |
| `UserRepository::find_by_email` | Exact lookup of the already-normalized email; return `Ok(None)` when absent. |
| `UserRepository::find_by_id` | Exact ID lookup; return `Ok(None)` when absent. |
| `ResumeRepository::create` | Persist all resume fields without vector precision or order loss. |
| `ResumeRepository::find_by_id` | Exact ID lookup; return `Ok(None)` when absent. |
| `ResumeRepository::list_by_user` | Return only records with the requested owner. Current ordering is unspecified. |
| `JobRepository::create` | Persist all job fields without vector precision or order loss. |
| `JobRepository::find_by_id` | Exact ID lookup; return `Ok(None)` when absent. |
| `JobRepository::list` | Return all jobs. Current ordering is unspecified and the method needs pagination before scale. |

Error translation should be stable and free of credentials or raw database data:

| Storage outcome | Domain result |
| --- | --- |
| Unique/key collision | `DomainError::Conflict` |
| Successful lookup with no record | `Ok(None)` |
| Invalid/corrupt stored shape | `DomainError::Internal` with sanitized context |
| Timeout, unavailable node, or exhausted transient retry | `DomainError::DependencyUnavailable` |
| Authorization failure at a database gateway | `DomainError::Internal` or `DependencyUnavailable`, logged securely for operators; never present it as end-user authorization. |

The adapter must validate deserialized UUIDs, timestamps, finite vectors, and
expected vector dimensions. It should attach request/operation context to logs but
must never log password hashes, JWTs, raw resumes, job descriptions, embedding API
keys, or database credentials.

## NenDB verification gate

Before choosing physical types or writing an adapter, verify and record:

- The authentic distribution, license, supported release, and maintenance status.
- A supported Rust driver or a documented HTTP/gRPC protocol with version policy.
- TLS and authentication behavior, timeout/cancellation support, and connection
  pooling guidance.
- Exact unique-index, atomic-create, transaction, consistency, and pagination
  guarantees under concurrent clients and failover.
- Maximum document/vector sizes, float fidelity, timestamp precision, and backup
  and restore behavior.
- Local and CI test infrastructure that does not depend on an unpinned image.

Until those checks and adapter contract tests pass, NenDB remains an intended,
unverified dependency and must not appear as a production service dependency.
